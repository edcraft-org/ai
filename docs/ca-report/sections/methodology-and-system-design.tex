\section{Methodology and system design}\label{sec:methodology}

\subsection{Technical problem and research questions}\label{sec:problem}

LLM-generated assessment questions can appear plausible while containing incorrect answers, faulty distractors or content that does not match the educator’s intentions. Reusable templates introduce a further concern: a fault in an answer or distractor recipe can affect several generated questions. Meanwhile, generating every question independently requires repeated model inference.

This project addresses these problems through reusable templates, execution-backed technical checks and feedback-guided revision. Difficulty and relevance assessments provide additional educational judgments, evaluated separately from technical correctness. Python tracing questions provide the initial implementation, while the architecture separates shared orchestration from domain-specific behavior.

The project investigates three research questions:

\begin{itemize}
\item RQ1: To what extent can technical checks identify faulty templates, and can feedback-guided revision repair them compared with generation without checking feedback?
\item RQ2: How do upfront authoring effort and the additional cost of reuse compare with one-shot template authoring and repeated direct-question generation?
\item RQ3: How closely do difficulty and relevance assessments agree with their recorded reference labels?
\end{itemize}

These questions require different evidence. Passing technical checks cannot establish educational alignment, while generating variants without further model calls does not by itself establish overall monetary savings.

\subsection{Requirements and scope}\label{sec:scope}

Appendix~\ref{app:user-stories}, Table~\ref{tab:user-stories} contains the detailed user stories, acceptance criteria and priorities. The project aims to support assessment authoring across subject domains, with Python tracing questions as the only currently implemented domain. The backend supports template authoring, checking, bounded revision and reproducible local expansion.

The intended workflow allows an educator to specify teaching requirements, obtain a checked template, review its content and supporting evidence, and approve it before generating question variants for learners. The current implementation provides the automated authoring and checking stages, while website integration, an enforced approval workflow, student-facing access, additional domains and source-grounded generation remain planned work.

A successful checking result indicates that the template passed the implemented checking policy. It does not replace educator review or approval before educational use.

\subsection{Architecture and separation of responsibilities}\label{sec:architecture}

The architecture separates provider communication, workflow coordination, domain logic and checking. This allows each component to change without requiring the others to reproduce its responsibilities.

\textbf{Component} & \textbf{Responsibility}\\
\midrule
Application & Coordinates authoring attempts, executes the frozen checking plan, manages revisions and determines the final outcome.\\
Provider adapter & Translates shared structured-generation requests into provider-specific API requests and normalises responses.\\
Domain module & Defines request and proposal schemas, builds candidates, binds checking inputs, saves eligible templates and expands them into questions.\\
MCP server & Exposes checking tools with defined input schemas, versions and evidence formats.\\
Saved artifact & Contains the reusable template, selected recipes, checking summaries and authoring provenance.\\
\bottomrule\end{tabularx}\end{center}

Provider adapters have been exercised with OpenAI, SoCLaaS and locally served models through Ollama. These integrations use different endpoints and response formats, which the adapters translate into the application’s shared structured-generation contract. This allows the same authoring workflow to operate across supported providers. However, compatibility still depends on the selected model’s ability to follow the proposal schema and fit within the available response budget. The models and configurations used in each experiment are reported in the evaluation chapter.

The application invokes checks directly through MCP. The authoring model selects checks and supplies their planning arguments in its initial structured response, but does not need to issue native tool calls. Domain-specific checking algorithms remain separate from provider communication. Additional domains would require their own schemas, checking capabilities and expansion logic; only the Python domain is currently implemented.

\subsection{Reusable templates and local expansion}\label{sec:templates}

Independent generation offers flexibility because each model call can produce a different question. However, it repeats inference and increases costs. Thus, this project concentrates generation and checking effort in a reusable template.

A Python tracing template contains a program, ordered finite parameter domains, question wording, an answer target, an answer recipe and distractor recipes. A recipe is an expression evaluated using the selected inputs. For example, a template whose program adds two inputs might use a + b as its answer recipe.

The earlier implementation enumerated input combinations within small domains and stored execution-derived answers. However, the number of combinations grows rapidly as more parameters or values are introduced. The current design therefore stores executable recipes and uses property-based testing to check them over a limited set of inputs. This supports larger declared domains but does not guarantee correctness for every permitted input.

Expansion loads the saved artifact, selects allowed inputs using a seed, evaluates the recipes and renders the question. It makes no model, MCP or program-execution call. Recipe failures or option collisions trigger resampling, with at most 32 attempts. This helps to generate variation of questions without the use of another model call.

Given the same saved artifact and seed, expansion is reproducible. However, different seeds may produce the same inputs or question, so reproducibility does not guarantee distinctness. The generated questions vary the input values while keeping the same program structure. They therefore provide repeated practice with the same underlying reasoning pattern, rather than introducing new algorithms or programming concepts.
